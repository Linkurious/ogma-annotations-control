Research: adding an author/link sub-section to Sticky Notes ​

Fact-finding only — no design proposal. Written for a design discussion about adding a "sub-section with author info etc." to Sticky Notes, with a free-form link at the bottom of the card, possibly shown only when the note is selected.

All citations are file:line in this repo unless noted otherwise.

1. Sticky Note is not a distinct data type — it's a styled Text annotation ​

There is no StickyNote type, class, or properties interface anywhere in the codebase. "Sticky note" is a drawing-mode preset: it creates a regular Text annotation (type: "text") with Miro-style default styling and no connector arrow.

  • packages/core/src/api/drawing.ts:31-52 — STICKY_NOTE_SIZE = 160 and defaultStickyNoteStyle (yellow #FFEB99 background, IBM Plex Sans, placeholder: "Quick note…", fixedSize: false).
  • packages/core/src/api/drawing.ts:262-313 — enableStickyNoteDrawing() / startStickyNote() call createText(x, y, 0, 0, "", { ...defaultStickyNoteStyle, ...style }) and note in comments: "It's a regular text annotation, so it goes through the same interactive corner-drag TextHandler.startDrawing() as startBox/startText".
  • packages/core/src/Control.ts:510-546 — public API doc for enableStickyNoteDrawing, same statement: "It's a regular text annotation, unlike enableCommentDrawing."
  • Data model: packages/core/src/types/features/Text.ts:33-48 — TextProperties (type: "text", content, width, height, style) and Text extends AnnotationFeature<GeoJSONPoint, TextProperties>. No author/id/link fields beyond the base AnnotationFeature (id, GeoJSON Feature shape) — see packages/core/src/types/features/Annotation.ts:9-30.
  • UI entry points that reference "sticky note" as a toolbar mode name only (not a data type): packages/core/src/ui/AnnotationToolbar.ts:23,34,42,254-263, packages/core/src/ui/icons.ts:32,67, packages/react/src/ui/AddMenu.tsx:17,45,149-154,204-210.
  • e2e coverage exists at packages/core/test/e2e/stickyNote.test.ts (behavior contract for placement/selection/editing), useful as a reference for what must keep working.

Open question: extending "sticky notes" specifically (vs. all Text annotations, since they're the same type) means either (a) adding the field to TextProperties generally, which would also affect boxes/plain text, or (b) inventing a way to distinguish "this text annotation is a sticky note" after creation (there is currently no such marker/flag persisted on the feature — the distinction only exists at creation time via the style preset).

2. author/timestamp fields already exist — but only on Comment, a different feature type ​

Comment (the chat-bubble, arrow-anchored callout — a separate annotation type from Text/sticky note) already has optional metadata fields:

ts
// packages/core/src/types/features/Comment.ts:71-93
export interface CommentProps extends AnnotationProps {
  type: "comment";
  content: string;
  mode: ...;
  width: number;
  height: number;
  /** Optional metadata */
  author?: string;
  timestamp?: Date;
  style?: CommentStyle;
}
  • Populated (optionally, both undefined by default) in createComment(): packages/core/src/types/features/Comment.ts:239-251.
  • Neither field is read anywhere else in packages/core/src or packages/react/src (no renderer, panel, or handler references .properties.author or .properties.timestamp — confirmed via repo-wide grep). They are typed but currently unused/undisplayed — i.e. plumbing exists but no UI surfaces them today, even on Comment.
  • No createdAt/updatedAt or any other author-like concept exists anywhere else in the codebase (checked across packages/core/src and packages/react/src, excluding tests).

Implication for the customer's ask: since Sticky Note = Text, not Comment, this existing author/timestamp shape isn't currently reachable by sticky notes at all. It's a precedent for where such fields would go (base *Props interface, optional, ?:) but not something sticky notes inherit automatically.

3. Selection state and how rendering differs when selected ​

Selection lives in a single Zustand-style store, not per-component React state:

  • packages/core/src/store/index.ts:87 — selectedFeatures: Set<Id> on AnnotationState.
  • Mutators: setSelectedFeatures, select, unselect, clearSelection, isSelected — packages/core/src/store/index.ts:428-457.
  • The SVG renderer subscribes to selectedFeatures (among other slices) and re-renders on change: packages/core/src/renderer/shapes/index.ts:56,68,82,164,219.

Existing precedent for "show X only when selected" at the shape level (the closest analog to the requested behavior) is on Comment, not Text: an edit-button badge is computed and rendered conditionally based on selection:

ts
// packages/core/src/renderer/shapes/comment.ts:446-450
const showEditBtn =
  mode !== COMMENT_MODE_COLLAPSED &&
  state.selectedFeatures.has(annotation.id) &&
  state.editingFeature !== annotation.id &&
  state.options.showEditButton;

This badge is a small foreignObject positioned in the corner of the comment box (packages/core/src/renderer/shapes/comment.ts:339-370), added to the group only if (showEditBtn).

The Text renderer (packages/core/src/renderer/shapes/text.ts) has no equivalent conditional content today — it always renders the same <rect> + <text>/<tspan> content regardless of selection state; only the background gets a hover-brighten effect (text.ts:70-76). Resize/drag handles for a selected shape are drawn by a separate renderer (packages/core/src/renderer/handles.ts:50, subscribes to selectedFeatures too), not by renderText.

Off-canvas alternative: there is a second place that already reveals UI "only when selected" — the AnnotationPanel (a plain HTML side panel, not part of the on-canvas SVG card):

  • Visibility state machine: packages/core/src/ui/panelVisibility.ts — attachPanelVisibility() shows the panel ~150ms after a single-annotation select event (long enough to distinguish a click from a drag-start, which cancels it) and hides on unselect/multi-select (panelVisibility.ts:47-127).
  • packages/core/src/ui/AnnotationPanel.ts:120-137 — setAnnotation() routes isText(...) || isBox(...) || isComment(...) to the same renderText() panel layout (AnnotationPanel.ts:161-182), i.e. the panel already treats sticky notes, plain text, boxes, and comments uniformly.
  • Panel content is built as HTML strings via a section(title, content) helper (AnnotationPanel.ts:199-201) and fully replaces this.panelBody.innerHTML on every selection change — a new "Author" section would slot in as one more ${this.section("Author", ...)} call in renderText().
  • Caveat: this panel currently only edits style (calls control.updateStyle(...), see doc docs/typescript/ui-components/style-panel.md:56-58 — "Editing a control calls control.updateStyle(...)"); it has no existing path for editing arbitrary content/metadata properties like an author name or URL, only style properties (color, background, font, stroke).

4. Card content/footer layout today (on-canvas SVG) ​

The on-canvas "card" is pure SVG, built imperatively in packages/core/src/renderer/shapes/text.ts — not an HTML/DOM element:

  • renderText() (text.ts:17-94) creates one <g class="annotation-text"> containing a single <rect> (background/border) and the text content.
  • Content is laid out by drawContent() (text.ts:154-243): measures/wraps text with @chenglou/pretext, then emits one <text> with one <tspan> per visible line, positioned by explicit x/dy offsets computed from padding and line height. There is no header/body/footer sectioning — it's a single text block that fills the box from the top, truncated with … if it overflows maxHeight/line count (text.ts:185-194).
  • There is no foreignObject in the Text renderer (unlike Comment, see below), so no CSS flexbox/grid "footer" area exists to slot new content into — adding one (e.g., a bottom-pinned link row) would mean either (a) more SVG <text>/<tspan> elements with manually computed y-offsets anchored to the box's bottom edge, similar to how the rect's height is used to place things, or (b) introducing a foreignObject into the Text renderer for the first time, as Comment already does.
  • Comment's box, by contrast, does use a foreignObject for its content (packages/core/src/renderer/shapes/comment.ts:310-337) with a real HTML <div> (padding, line-height, overflow, pointer-events toggling so clicks pass through to the background <rect> except on links/buttons). This is the more natural existing pattern to extend for an HTML-laid-out footer sub-section, and it's already selection-gated for the edit button (§3).

5. Existing "link"/URL patterns ​

Two unrelated concepts both use the word "link" in this codebase — worth flagging to avoid confusion in the design discussion:

(a) Auto-detected URLs inside annotation text — the closest existing precedent for a "free-form link":

  • packages/core/src/utils/rendering.ts:7,39-41 — ANNOTATION_LINK_CLASS = "ogma-annotation-link" and createUrlPattern() returning /(https?:\/\/[^\s<]+)/g.
  • Used in the Text renderer to turn any http(s)://… substring typed into the content into a clickable SVG <a> inside a <tspan>: packages/core/src/renderer/shapes/text.ts:213-231.
  • Used in the Comment renderer's formatContent() to do the same via HTML string replacement into the foreignObject's <div>: packages/core/src/renderer/shapes/comment.ts:384-403.
  • packages/core/src/utils/rendering.ts:9-25 — isAnnotationLinkTarget() lets click handlers detect a click landed on one of these auto-links and skip selection/edit-mode entry instead (packages/core/src/interaction/index.ts uses this pattern; confirmed via the .ogma-annotation-link class name shared between renderer and interaction code).
  • This is auto-detection inside free-typed body text, not a discrete "link" field on the annotation's properties. A "free-form link at the bottom of the card" as a dedicated field would be new: no annotation type currently has a structured url/link string property.

(b) Link/ExportedLink — an unrelated, pre-existing concept: structural attachment of an arrow to another annotation or graph node/edge, stored on arrow.properties.link. Nothing to do with URLs.

  • packages/core/src/types/features/Link.ts:33-63 — Link (arrow, id, side, target, targetType, magnet) and ExportedLink (serialized form).
  • Documented in docs/typescript/core-concepts/annotations.md:250-351 ("How Links Work", "Creating Links", etc.) — entirely about arrow connectors, e.g. "Links are stored in the arrow.properties.link property" (annotations.md:267).

Naming risk: calling the new sticky-note feature a "link" field risks colliding with this existing Link/link vocabulary that means something structurally different (arrow attachment) elsewhere in the same codebase and docs.

6. Serialization / schema conventions ​

  • Annotations serialize as plain GeoJSON Features — no custom envelope, no schema-version field found anywhere in packages/core/src or packages/react/src. Confirmed via repo-wide search for createdAt|updatedAt|schema.*version (only hits were an unrelated updatedAttributes parameter in packages/core/src/handlers/links/sync.ts:169-174, not a schema version).
  • docs/AI_REFERENCE_TYPESCRIPT.md:665 — "All annotations are based on the GeoJSON specification..., making them easy to serialize, store, and share."
  • No migration helper, versioning field, or upgrade path exists for annotation shapes in this codebase today. Adding a new optional property (e.g. link?: string, author?: string) to TextProperties would be a purely additive, backward-compatible change under this convention (old saved annotations simply lack the field) — but there is no established process (e.g. a version bump, a migrate-on-load step) for such changes; this would be new territory, not something to follow an existing pattern for.

7. Where research/design notes live in this repo ​

No existing notes/, ADR/, or research-doc folder was found anywhere in the repo (checked for ADR, RFC, research in file/dir names, and for a CONTRIBUTING.md — none exist). docs/ is a published VitePress documentation site (docs/.vitepress/, docs/typescript/, docs/react/, docs/architecture/ for diagrams) rather than a place for working notes — its content is user-facing reference material, generated from JSDoc in part (docs/typescript/api/**).

Since there's no established convention, this file was placed at docs/notes/sticky-note-author-link-research.md, alongside (but clearly separated from) the published docs, following the existing docs/<topic>/ sub-folder pattern used elsewhere (docs/architecture/, docs/typescript/). If the team has a different preferred location (e.g. outside docs/ entirely so it doesn't ship with the VitePress build), this should move.

Summary of open questions for the design discussion ​

  • Sticky Note = Text annotation with a style preset, not a distinct type — should the new fields go on TextProperties generally (affecting boxes/plain text too), or does "sticky note" need to become a distinguishable/persisted sub-type first?
  • Comment already has unused author?/timestamp? fields with no reader anywhere — worth deciding whether to finally wire those up as the model for the new fields, or design fresh.
  • On-canvas Text rendering is pure SVG with no footer/section concept and no foreignObject today; Comment's foreignObject + selection-gated edit-button badge is the closest existing pattern for "extra chrome shown only when selected."
  • The off-canvas AnnotationPanel already shows/hides on selection and already unifies Text/Box/Comment, but it currently only edits style, not content/metadata — extending it to author/link would be new capability for that component, not just a new section.
  • "Link" as a name collides with the pre-existing arrow.properties.link (attachment) concept; the closest existing "link" behavior is auto-detected URLs inside typed content, not a discrete field.
  • No schema-versioning/migration convention exists in this codebase; adding fields is additive/backward-compatible by default but there's no process to model against.
