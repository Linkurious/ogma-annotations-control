Industrial-grade gap analysis ​

Fact-finding against primary sources only (source, config, CI, git history — no external best-practice references taken on faith). Scope: what's missing for this library to be "industry best / industrial grade" — stability, code quality, release hygiene. All citations are file:line or command output from this repo (develop branch, HEAD a21089b) unless noted. Ends with a prioritized P0/P1/P2 punch list as requested.

Out of scope by request: whether CI should move from Jenkins to GitHub Actions, and open-source contributor hygiene (CONTRIBUTING.md, CODE_OF_CONDUCT.md, issue/PR templates) — this is an internally-consumed library, not a community-driven OSS project, so neither is a relevant gap here.

  • packages/core also has a dedicated e2e suite, packages/core/test/e2e/*.test.ts (10 files: creation, comment, stickyNote, multiSelectDrag, anchorFollow, offsetContainer, lockedAndHidden, snapping, drawing, smallFontCulling), driven by Playwright/Chromium via a custom vitest config (packages/core/test/e2e/vitest.config.mts:1-33, retry: 2, maxWorkers: 2, hookTimeout: 60000 — config comments describe real CI flakiness tuning, e.g. "a test that takes ~6s locally took 47s in CI").
  • A benchmark script exists: packages/core/package.json:64 — "test:benchmark": "vitest bench --run".
  • Root workspace also runs a small dependency-floor test: test/index.test.ts via test/vitest.config.mts and scripts/test-ogma-floor.mjs (package.json:9-13), which checks behavior against the declared minimum Ogma peer version.

Exists:

  • strict: true in both packages: packages/core/tsconfig.json:14, packages/react/tsconfig.json:26. Both also set noUnusedLocals/noUnusedParameters/noImplicitReturns (packages/core/tsconfig.json:15-17, packages/react/tsconfig.json:27-30), and react additionally sets noFallthroughCasesInSwitch (packages/react/tsconfig.json:29).
  • @ts-ignore/@ts-expect-error usage is minimal (3 occurrences total, repo-wide, all @ts-expect-error — never the unchecked @ts-ignore) and each is a one-line, explained escape hatch for accessing private/undocumented Ogma internals: packages/core/src/handlers/links/geometry.ts:177 (// @ts-expect-error curvature exists on edges), packages/core/src/handlers/links/sync.ts:132 (// @ts-expect-error private event), packages/core/src/handlers/snapping/edge.ts:102 (// @ts-expect-error curvatures exist is a private readonly attribute).

  • typescript: 5.3.3 pinned identically in both packages' devDependencies (packages/core/package.json, packages/react/package.json).

Missing / weak:

  • No noUncheckedIndexedAccess or exactOptionalPropertyTypes in either tsconfig (grep -rn "noUncheckedIndexedAccess\|exactOptionalPropertyTypes" packages/*/tsconfig*.json → no hits) — the strict baseline is solid but not maximal; index/record access (e.g. state.features[id], seen throughout packages/core/src/store/index.ts) is not compiler-checked for possible undefined.
  • No .d.ts/type-level tests (no tsd, expect-type, or // $ExpectType usage found) to guard the public API's exported type surface against accidental narrowing/widening across releases.

6. Error handling & runtime robustness ​

Exists:

  • The store layer validates permission preconditions (editability, cascade-delete safety) before mutating state, always failing soft with a logged error rather than throwing or silently corrupting state — e.g. packages/core/src/store/index.ts:226-270 (removeFeature): checks !state.options.isEditable(feature) → console.error(...); return state (unchanged), checks for an orphaned comment before allowing its last arrow to be deleted, and refuses a whole cascade delete if any member is non-editable. The same guard pattern recurs at packages/core/src/store/index.ts:420 (update) and packages/core/src/handlers/arrow.ts:330 (link creation).
  • User-authored text rendered via innerHTML in the Comment renderer is explicitly HTML-escaped first: packages/core/src/renderer/shapes/comment.ts:384-391 (formatContent() replaces &, <, > before any further processing), and only then has URLs turned into anchors via a tightly-scoped https?:// regex with target="_blank" rel="noopener noreferrer" (comment.ts:397-401, pattern from packages/core/src/utils/rendering.ts:7,39-41) — this is a correct, deliberate escape-then-linkify order, not a raw-HTML injection risk.
  • Seven try/catch blocks exist at points doing genuinely fallible work (SVG/font/DOM operations): packages/core/src/renderer/shapes/text.ts, packages/core/src/renderer/shapes/index.ts, packages/core/src/handlers/links/geometry.ts, packages/core/src/handlers/links/sync.ts.
  • packages/core/src/Control.ts:984 throws a descriptive Error for a clearly-programmer-error case (getArrow on a non-existent id): if (!arrow) throw new Error(`Arrow with id ${arrowId} not found`);.

Missing / weak:

  • No input validation at the public data-ingestion boundary.packages/core/src/api/update.ts:24-32 (UpdateManager.add) accepts any Annotation | AnnotationCollection, runs a format migration (migrateBoxOrTextIfNeeded), and pushes straight into the store with no shape/type check — no verification that annotation.id exists, that annotation.geometry is well-formed GeoJSON, or that annotation.type is one of the known feature types. Repo-wide, grep -rn "throw\|Error(" packages/core/src/api/*.ts returns zero matches — none of comments.ts, drawing.ts, history.ts, selection.ts, update.ts throws or constructs an Error anywhere. Malformed annotation data (e.g. loaded from an external/legacy save) is trusted as-is; failure mode on bad data is presumably a downstream renderer crash rather than a clear validation error at the boundary where it entered.
  • No React error boundary exists in packages/react/src (grep -rln "componentDidCatch\|ErrorBoundary" packages/react/src → no hits) — a render-time exception inside the annotation UI tree (e.g. from the untested ui/ components, dimension 1) would propagate up and unmount the host application's React tree rather than being contained.
  • console.error is the library's only "reporting" channel for the guard failures above — there's no structured error/event (e.g. an emitted "error" event with a code) a host application could subscribe to and handle programmatically instead of scraping the console. Several of these sites carry // eslint-disable-next-line no-console right above them (packages/core/src/store/index.ts:233,245,265, packages/core/src/ui/AnnotationPanel.ts:114), confirming no-console is the linted-for default and these are deliberate, acknowledged exceptions — but still means failures are only observable by reading the browser console, not catchable by the host app.
  • Found 2026-09-22, not fixed here (out of scope for the a11y pass that surfaced it): clicking any button inside the React AnnotationPanel (a color swatch, a background swatch, opening the Font dropdown — even ones that don't call editor.updateStyle) immediately deselects the annotation and closes the panel, in the unmodified packages/react/web demo app on develop (reproduced via a headless-browser click before any UI changes were made, to rule out a regression from this session's own edits). AnnotationPanel.tsx:160-173's stopEvent handler calls evt.stopPropagation() on onClick/onMouseDown/onMouseMove at the panel root specifically to prevent exactly this — so either that propagation-stopping isn't reaching whatever listener is deselecting (e.g. a capture-phase document listener, which fires before a bubble-phase stopPropagation further down the tree could block it), or the deselection is triggered some other way entirely. Root cause not diagnosed — flagging as a real, reproducible interaction bug for whoever picks it up next; every panel control is currently a one-click-then-gone experience for a mouse user too, not just a keyboard-user a11y gap.

7. Browser/bundle concerns ​

Exists:

  • Both packages build with Vite library mode, emitting ESM (.mjs) and CJS (.js), no UMD (explicitly ruled out for react: "Multi-entry libs cannot use UMD; emit ESM (.mjs) and CJS (.js)", packages/react/vite.config.ts:29-30; core has an "./umd" export subpath in packages/core/package.json:32-36 but it actually points at the same .js/.mjs CJS/ESM outputs, not a true global/IIFE UMD bundle).
  • Modern package exports maps with types/import/require/default conditions for multiple subpaths (., ./ui, ./ui/styles.css or ./style.css, ./esm) in both packages/core/package.json:12-46 and packages/react/package.json:18-33.
  • Peer dependencies correctly externalize the host libraries instead of bundling them: @linkurious/ogma is a peerDependency (>=5.3.11) in both packages, react >=17 is a peer dep of packages/react (packages/react/package.json:46-49), and both Vite configs list them (plus @linkurious/ogma-react, @linkurious/ogma-annotations(-react), vanilla-colorful) under rollupOptions.external (packages/core/vite.config.ts:25-26, packages/react/vite.config.ts:33-42).
  • packages/react/package.json:13-15 declares "sideEffects": ["dist/**/*.css"], correctly scoping tree-shaking side-effect exemptions to just the CSS files.
  • A CSS-in-JS injection plugin is used for the React build (vite-plugin-lib-inject-css, packages/react/vite.config.ts:3,17) so consumers don't have to manually import a separate stylesheet for component styles beyond the dedicated ui/styles.css export.
  • Control type identity is deliberately kept singular across the index/ui entry points via a real chunked .d.ts build (scripts/build-types.mjs, rollup-plugin-dts) instead of Vite's default per-entry declaration bundling — extensively documented in packages/core/vite.config.ts:5-13 and packages/react/tsconfig-build.json:1-24 as a deliberate fix for a previously-real "editor is undefined" dual-context bug (packages/react/vite.config.ts:37-39 comment).

Missing / weak:

  • packages/core/package.json has no "sideEffects" field at all (only packages/react/package.json declares one) — despite core also shipping a CSS file ("style": "dist/ogma-annotations.css", packages/core/package.json:9). Without an explicit sideEffects marker, bundlers must conservatively assume the whole package has side effects, which weakens tree-shaking for consumers who only import a few functions from core (e.g. just createArrow/createText without the Control/ui machinery).
  • Source maps are explicitly disabled in the core build: packages/core/vite.config.ts:15 — sourcemap: false. React's vite.config.ts doesn't set the option at all, which is Vite's false default too (confirmed: grep -n "sourcemap" packages/react/vite.config.ts → no match). Neither published package ships source maps, so debugging a consumer-reported stack trace against a minified build (minify: true, packages/core/vite.config.ts:27) requires the library author to reproduce locally rather than read the trace directly.
  • No bundle-size tracking/budget tooling (size-limit, bundlesize, bundlewatch — grep -rn "size-limit\|bundlesize\|bundlewatch" across all package.json files: no hits) — bundle size regressions between releases aren't measured or gated anywhere.
  • No true UMD/global (<script>-tag-consumable, IIFE with a global var) build exists for either package despite package-lock.json/exports naming an "./umd" subpath — it's CJS under a different label, not a browser-global bundle, so a non-bundler, no-build-step consumer (plain <script src=...>) has no supported entry point.

8. Accessibility ​

packages/react/src/ui (React UI layer) — closed 2026-09-22.packages/core/src/ui (vanilla imperative toolbar/panel) — still open, see below.

  • Every icon-only control across all 16 packages/react/src/ui/** components now carries aria-label (mirroring the existing data-tooltip text — that text was already CSS ::after/::before content, which is not exposed to the accessibility tree, so it was previously invisible to screen readers despite being visible to sighted mouse users), plus aria-pressed on toggle-state buttons (AddMenu's drawing-tool/erase buttons, LineTypeController, BackgroundController, ColorController swatches) and role="group"/aria-label on the toolbar/swatch-row containers.
  • FontController and ExtremityController's "custom-select" dropdowns were plain, unlabeled, keyboard-unreachable <div>s with onClick handlers (no tabIndex, no role, no way to reach or operate them without a mouse). Converted to real <button type="button"> elements (trigger + each option) with aria-haspopup="listbox"/aria-expanded on the trigger and role="listbox"/role="option"/aria-selected on the option list — native Tab/Enter/Space now reaches and operates every option; the trigger also closes on Escape. packages/core/src/ui/styles.css's .custom-select-option rule had no background/border reset in its base (non-hover/non-selected) state (only :hover/.selected set background) — converting to <button> would have shown default browser button chrome without also fixing that rule, so it was closed too (background: transparent; border: none; added, verified visually before/after via a headless-browser screenshot comparison against unmodified develop).
  • SliderController's <input type="range"> had no accessible name at all (a sibling <h3> showed the label visually but wasn't programmatically associated) — now carries aria-label from the same title prop already rendered.
  • Icon.tsx's SVGs are now aria-hidden="true" (decorative — the parent control supplies the accessible name), and AnnotationPanel's root is role="region"/aria-label="Annotation style panel" for landmark navigation.
  • Still open in packages/react: no roving-tabindex/arrow-key navigation within an open listbox (Tab moves through every option one at a time, which is keyboard-operable but not the full ARIA listbox pattern); no live-region announcement of selection/drawing-mode changes; the third-party <rgba-color-picker> custom element's internal accessibility (inside ColorController's picker overlay) is out of this package's control.
  • packages/core/src/ui (vanilla toolbar/panel) is a separate, still-open gap — same imperative-DOM-construction pattern as before (packages/core/src/ui/toolbar/cells/dropdown.ts:48, packages/core/src/ui/toolbar/cells/buttonItem.ts:21, packages/core/src/ui/AnnotationToolbar.ts:341), still only the one pre-existing aria-pressed hit (packages/core/src/ui/toolbar/cells/buttonItem.ts:33). Not touched by this pass — the shared styles.css fix above benefits it for free, but the imperative TS itself needs the same aria-label/role/keyboard treatment applied separately, since it's a different codebase (no JSX) from the React work done here.
  • No accessibility linting is configured — no jsx-a11y (or oxlint a11y category) plugin in the shared or per-package oxlint config (dimension 3) — still open, would have caught this gap automatically.
  • Still consistent with the product surface: a canvas-drawing tool (arrows, text boxes positioned by mouse drag) is inherently hard to make fully keyboard-accessible for the drawing interactions themselves (no keyboard alternative for placement exists yet) — this pass covered the panel/toolbar chrome around that canvas, not the canvas interaction itself.

9. Security posture ​

Exists:

  • npm audit --omit=dev (production dependency tree only): 0 vulnerabilities.
  • Full npm audit (including devDependencies): 8 vulnerabilities (5 low, 2 moderate, 1 high), all in the dev/build toolchain, not shipped code: a @tootallnate/once → http-proxy-agent → jsdom chain pulled in transitively by svg-text-to-path (a dependency of @linkurious/svg-font-embedder, a devDependency), and an esbuild issue pulled in transitively by vitepress's bundled vite. Missing / weak:

  • npm audit is not run in CI as far as this repo shows — Jenkinsfile doesn't reference audit anywhere, and whether the opaque external Jenkins shared library covers it can't be confirmed from primary sources (dimension 4) — dependency vulnerabilities are only caught if someone runs npm audit manually or Renovate happens to open an update PR.
  • Other innerHTML call sites in packages/core/src/ui/ and packages/core/src/renderer/shapes/ (dropdown.ts:48, buttonItem.ts:21, AnnotationToolbar.ts:341, arrow.ts:117, index.ts:92,186, comment.ts:286,366) all assign either "" (clearing) or the result of svgIcon(...) (an internal, non-user-controlled icon name) — these are not user-data-reachable, so they don't carry the same XSS surface as comment.ts:335, but this was only confirmed by reading each call site individually; there's no lint rule or convention in this codebase flagging innerHTML assignments for manual security review (e.g. no eslint-plugin-securityor oxlint equivalent enabled).

10. Backward compatibility / semver discipline ​

Exists:

  • Version is kept in lockstep across root, packages/core, and packages/react — all read 2.1.4 (package.json:3, packages/core/package.json:2, packages/react/package.json:2), enforced by the sync_versions postversion hook (root package.json:22) and packages/react/package.json:16's postversion re-pinning its @linkurious/ogma-annotations dependency to the exact new version.
  • Git tags are a clean, monotonic semver sequence (v1.1.1 → v2.1.3, git tag | sort -V), and a real major bump exists in history (v1.1.27 → v2.0.0, commits 2df13ac/6bc2ed3), evidence the project has exercised the major-version-for-breaking-change discipline at least once (that release included a package rename — see commit 1c5a4e3 Fix npm publish path in Jenkinsfile after renaming of package.).
  • An explicit backward-compat shim exists in code: packages/core/src/api/update.ts:29 (migrateBoxOrTextIfNeeded(annotation)) runs on every add() call to migrate an old Polygon-based Box/Text geometry format to the current Point-based format — a real, live example of additive/non-breaking data evolution.
  • The peer dependency floor is actively tested, not just declared: scripts/test-ogma-floor.mjs + root package.json:10-11 (test:ogma-floor, e2e:ogma-floor) run the suite against the minimum declared Ogma version (ogma-5-3-11 devDependency aliasing @linkurious/ogma@5.3.12, root package.json:66) to catch accidental use of newer Ogma APIs than the declared >=5.3.11 peer range allows.

Missing / weak:

  • No CHANGELOG (dimension 4) means there's no per-version record of what was additive vs. breaking — a consumer has to read raw commit history or diff dist/types between tags to know.
  • No deprecation pattern found in code: grep for @deprecated JSDoc tags was not run as an exhaustive scan here, but no deprecated-API affordance (e.g. a runtime deprecation warning helper) exists in packages/core/src/api/*.ts or Control.ts — old API surface appears to be removed/renamed directly rather than soft-deprecated first (consistent with the 2.0.0 rename event above having no visible transition period in this repo).
  • Git tags currently lag package.json's version by one patch release (dimension 4) — semver-as-documented-in-tags is presently unreliable.
